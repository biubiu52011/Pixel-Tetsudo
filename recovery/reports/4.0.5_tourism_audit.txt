# 4.0.5 — Tourism: First-Time User IA Audit
# Date: 2026-08-31
# Rule: AUDIT ONLY — NO CODE CHANGES

---

## Executive Summary

The Tourism module has two distinct surfaces: the **Home page grid** (sightseeing.js) and the **Detail page** (tourism-detail.js). The detail page correctly implements language-aware display names, but the Home page grid does not — it shows raw English spot names to all users. Additionally, 3 tag filter keys are missing from translations (carried over from 4.0.2). The underlying tourism data is monolingual (English only), which limits what can be fixed at the code level.

---

## F-TM01 🟡 QUESTIONABLE — Home Page Spot Grid Shows Raw English Names

**Location:** `js/sightseeing.js:238`
```js
const name = s.name || '';
...
'<h3>' + name + '</h3>' +
```

**Problem:** The spot card grid on the Home page uses `s.name` directly — the raw English name from `railway_data.json` (e.g., "Local Shrines", "Station Area", "Shopping Street"). There is no language resolution for spot names in the grid view.

**What the user sees (JA mode):**
```
[Local Shrines]    ← English name in Japanese UI
[Station Area]     ← English name in Japanese UI
```

**Detail page contrast:** `tourism-detail.js:55-59` correctly uses:
```js
function getSpotName(spot) {
  var l = lang || 'ja';
  if (spot['name_' + l]) return spot['name_' + l];
  if (spot.name) return spot.name;
  return '';
}
```

**Root cause:** The tourism data (`railway_data.json`) only has English `name` fields — no `name_ja`, `name_zh`, `name_ko` variants exist. The detail page's `getSpotName()` would work correctly IF the data had multilingual fields, but the data doesn't. The grid view doesn't even attempt language resolution.

**User impact:** Medium. Non-English users see English spot names on the Home page. The detail page also falls back to English since the data lacks multilingual fields.

**If fixed at code level only:** At minimum, the grid should use `getSpotName()` pattern (even if it falls back to English). This ensures consistency between grid and detail views. A complete fix requires adding multilingual spot names to the data.

**Category:** INFORMATION_OVERLOAD / INCONSISTENCY

## F-TM02 🟢 GOOD — Detail Page Uses Language-Aware Spot Names

**Location:** `js/tourism-detail.js:55-59`
```js
function getSpotName(spot) {
  if (!spot) return '';
  var l = lang || 'ja';
  if (spot['name_' + l]) return spot['name_' + l];
  if (spot.name) return spot.name;
  return '';
}
```

**Why it works:** The detail page correctly attempts language-specific name resolution. If multilingual data were added, this would work immediately. The fallback chain is sensible.

**Limitation:** Current data only has English `name` fields, so all languages fall back to English. This is a DATA limitation, not a code bug.

**Category:** GOOD (code is correct; data is the bottleneck)

## F-TM05 🟢 GOOD — Station Labels Use Language-Aware Resolution

**Location:** `js/tourism-detail.js:48-53`
```js
function getStationLabel(key) {
  var nm = getNameMap();
  if (nm[key] && nm[key].zh) return nm[key].zh;
  if (nm[key] && nm[key].ja) return nm[key].ja;
  if (nm[key] && nm[key].en) return nm[key].en;
  return key;
}
```

**Why it works:** Station names in the detail page use the name_map from RailwayDB, which has ja/zh/en keys.

**Category:** GOOD

## F-TM06 🟠 WEAK — Hours/Fees Show "Data Unavailable" for All Spots

**Location:** `js/tourism-detail.js:219-223`
```js
'<div class="info-row"><span class="info-label">' + t('detail.info_hours') + '</span><span class="info-value">' + escapeHtml(t('detail.unavailable')) + '</span></div>'
+ '<div class="info-row"><span class="info-label">' + t('detail.info_fee') + '</span><span class="info-value">' + escapeHtml(t('detail.unavailable')) + '</span></div>'
```

**Problem:** Every spot detail page shows "Data unavailable. Please refresh." for hours and fees. This is because the tourism data doesn't include `hours` or `fee` fields. Every user sees this placeholder for every spot.

**User impact:** Medium. This creates a poor first impression — the detail page looks incomplete. Users may think the app is broken or the data is missing.

**Analysis:** The question is whether this information is essential. For a railway tourism app, operating hours and fees are useful but not critical. However, showing a persistent "unavailable" message is worse than simply not showing the field.

**If removed:** The hours/fees section would disappear, and the detail page would look cleaner. Users who need this info would search elsewhere.

**Recommendation:** Either remove the hours/fees section entirely (since no data exists), or populate it with real data. The current "always unavailable" state is worse than absent.

**Category:** WEAK

## F-TM08 🟡 QUESTIONABLE — Home Page Mixes Tourism With Route Search

**Location:** `pages/home.html:48-96`

The Home page has two modules in one tab:
1. Route Search (search-card)
2. Tourism/Sightseeing (sm-module)

**Analysis:** This was flagged in 4.0.1 as a layout inconsistency. The two modules have different interaction models (search form vs. station picker + tag filters + grid). They share visual language (pixel-card, module-title) but feel like different products.

**User impact:** Low-medium. Users can access both features from Home, but the visual weight is uneven (tourism module is more complex).

**Recommendation:** Consider whether tourism should be a separate top-level tab or remain on Home. This is an IA decision, not a bug.

**Category:** QUESTIONABLE (information architecture)

## F-TM12 🔵 INTENTIONAL — No Operator/Line Filtering in Tourism

**Observation:** Tourism has tag-based filtering (history, nature, shrine, food, etc.) but no operator or line-based filtering.

**Analysis:** This is appropriate. Tourism spots are organized by interest category, not by railway line. A user looking for "food near Shinjuku" doesn't care which train line they took. The tag system is the right abstraction.

**Category:** INTENTIONAL
