## 6. Cross-Module Coupling Analysis (P2 Findings)

### P2-01: history.js monkey-patches SearchUI.performSearch

Location: js/history.js:164-192

Pattern:
- history.init() saves original SearchUI.performSearch
- Replaces with wrapper that:
  a) calls original
  b) reads this.fromInput / this.toInput (internal props)
  c) saves to history

Risk: If SearchUI.performSearch signature changes, history breaks silently.
      If SearchUI renames fromInput/toInput, history breaks.
      History reads SearchUI internal state (not public API).

Verdict: MEDIUM RISK - functional now, but fragile under refactoring.

### P2-02: history.js.restoreFromRecent() accesses SearchUI internal DOM

Location: js/history.js:214-226

Pattern:
- history.restoreFromRecent(fromId, toId)
  -> window.SearchUI.fromInput.value = fromName
  -> window.SearchUI.toInput.value = toName
  -> dispatchEvent(input) on both

Risk: Directly manipulates SearchUI internal DOM elements.
      Relies on SearchUI having fromInput/toInput properties.
      If SearchUI restructures its DOM, this breaks.

Verdict: MEDIUM RISK - same category as P2-01.

### Not a Bug, But a Design Debt
These patterns are FUNCTIONAL and intentional (history auto-save and restore).
However, they violate the module boundary principle.
The fix would require SearchUI to expose public APIs:
  SearchUI.getInputs() -> { from, to }
  SearchUI.setInputs(fromValue, toValue)
  SearchUI.onSearchComplete(callback)
This is a 4.2.x improvement task, not a blocking issue.
