D. CSS ARCHITECTURE
============================================================

File                  | Chars   | Classes | Purpose
style.css             | 29,967  | 158     | Global+Route+RT+History+Journey+Nearby
tourism-styles.css    | 22,334  | 108     | Tourism specific
lang-bar.css          | 5,022   | ~20     | Language switcher
realtime.css          | 3,315   | 21      | RT-specific (UNDERUSED)
trains.css            | 1,887   | ~15     | Trains detail
TOTAL: ~62,525 chars, ~322 unique classes

Issues:
1. style.css is a dumping ground (29,967 chars, 158 classes)
   Contains: global vars, line cards, realtime UI, history, journey,
   nearby spots, search UI, mobile responsive, filter bar
   Risk: High coupling, hard to locate specific styles

2. realtime.css exists but is mostly empty
   Most RT styles ended up in style.css instead
   Question: Should realtime.css be populated or removed?

3. Three @media (max-width: 640px) blocks in style.css
   Each serves different feature. Should be consolidated.

4. .home-search-priority { order: -1; } and .home-tourism-secondary
   Implementation details leaked to CSS. Secondary is unused.

5. Duplicate .journey-arrow and .journey-transfers definitions
   Intentional responsive overrides but could be consolidated.

Specificity: !important=1, high-specificity=7, cross-file conflicts=0
Assessment: Well-controlled, no major cascade risks.

H. FINAL PRODUCT JUDGMENT
============================================================

### 1. Does Pixel-Tetsudo have its own visual language?
YES, but incomplete.
Pixel-art aesthetic (box shadows, pixel font, green brand) creates identity.
However, visual language is NOT consistently applied:
- Journey card dark gradient differs from light pixel-card aesthetic
- Tourism has its own system (.sm-card, .article-hero) not integrated with main cards
- Realtime line cards (.rs-line-card) differ from home/search cards

### 2. Can a first-time user understand the product?
PARTIALLY.
- Home: Search form visible but browse-lines content competes for attention
- Route results: Journey card is prominent with clear hierarchy
- Realtime: Status indicators clear, operator grouping logical
- Trains: Line list clear, detail view good info density
- History: Functional but visually unremarkable

MAIN ISSUE: Home has no clear PRIMARY action. Both Route Search and
Tourism presented as equal modules. User might not know which to use first.

### 3. Can a new AI developer navigate correctly?
MODERATE RISK.
Strengths: CSS variables consistent, class naming follows patterns,
RailwayDB is single source of truth for display names.

Risks: style.css too large, realtime.css misleading, no architecture docs,
dead CSS classes persist, .pixel-card/.search-card relationship unclear.

RECOMMENDATIONS

PRIORITY 1 (Design System Foundation):
  - Create component catalog documenting each card type
  - Decide: is .search-card a real component or wrapper?
  - Consolidate three @media blocks into one
  - Remove .home-tourism-secondary (dead CSS)

PRIORITY 2 (Home Page Hierarchy):
  - Make Route Search visually dominant
  - Make Tourism clearly secondary
  - Consider: should Route Search be the ONLY thing on Home?

PRIORITY 3 (CSS Architecture):
  - Split style.css with clear section comments
  - Decide fate of realtime.css
  - Add architecture comments to CSS

PRIORITY 4 (Not in 4.2 scope):
  - Journey card visual redesign
  - Tourism module reorganization
  - New component library
