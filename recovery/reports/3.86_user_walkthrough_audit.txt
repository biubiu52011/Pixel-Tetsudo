## Finding-by-Finding Audit

### P2-01: Operator names show raw IDs everywhere

**Category:** TECHNICAL-LEAK / UX_INCONSISTENCY
**Severity:** P2
**User impact:** High — a Japanese user sees "JR-East" instead of "JR東日本"; a Chinese user sees "TokyoMetro" instead of "东京地铁"

**Root cause:**
```
window.tOp(name)  →  checks window.tOp  →  undefined
                   →  checks TransitConstants.OP_NAMES[name]  →  {} (empty)
                   →  falls back to raw name: "JR-East"
```

Locations affected:
- `data-state.js:237` — Trains operator group titles (`<div class="rs-operator-title">`)
- `realtime-view.js:136` — Realtime filter bar buttons
- `trains-detail.js:119` — Detail page info row (operator field)

**Evidence:**
```js
// js/common.js — TransitConstants.OP_NAMES is EMPTY
window.TransitConstants = {
  OP_ORDER: ["JR-East", "JR West", "TokyoMetro", ...],
  NORMALIZE: {},
  OP_NAMES: {}   // ← EMPTY — no operator name translations
};

// js/data-state.js — tOp() depends on window.tOp
function tOp(name) {
  return (window.tOp && window.tOp(name)) || name || "";
}
// window.tOp is never set by any script
```

**translations.js has no operator name keys** — there are no `"op.JR-East"`, `"op.TokyoMetro"`, etc. entries in any language section.

**Recommendation:** Add operator name translations to `translations.js` for all 4 languages, then populate `TransitConstants.OP_NAMES` or set `window.tOp` during i18n init. This is a data + one-line wiring fix, not an architecture change.

**Does a regular user care?** YES — this is the most visible issue on every page.

### P3-01: Detail page title always shows Japanese name

**Category:** INFORMATION_ARCHITECTURE
**Severity:** P3
**User impact:** Low — Japanese is the default and primary language; English/Chinese/Korean users still see Japanese line names

**Root cause:**
```js
// js/data-state.js:renderCard() & js/trains-detail.js
var displayName = (line && line.nameJa) || (line && line.nameEn) || (line && line.name) || lineId;
// This hardcodes nameJa priority regardless of currentLang
```

The `getDisplayName()` function in `realtime-view.js` has the same pattern.

**Evidence:**
```js
// trains-detail.js showDetail()
'<h2 class="detail-title">' + escapeHtml(line.nameJa || line.nameEn || line.name || lineId) + '</h2>'

// realtime-view.js openModal()
modal.querySelector(".rs-modal-title").textContent = getDisplayName(line) || tLine(line.id) || line.name;
// where getDisplayName = (line.nameJa) ? line.nameJa : ...
```

**Recommendation:** Make detail title respect `window.currentLang` by checking `name{lang}` first, falling back to `nameJa`. This is a small logic change, not a data change.

**Does a regular user care?** Some — a Chinese user opening the detail page for 中央線快速 would expect to see "中央线快速" not "中央線快速".

### P3-02: Line code badge in detail header is redundant with card badge

**Category:** DUPLICATE_INFORMATION
**Severity:** P3
**User impact:** Low — the colored code badge (JC, JB, etc.) appears both on the card and in the detail header

**Evidence:**
```js
// trains-detail.js
'<div class="detail-code" style="background:...">' +
  '<span class="detail-code-text">' + escapeHtml(line.code || "") + '</span>' +
'</div>'
```

**Recommendation:** KEEP — the code badge in detail header provides quick visual identification when scrolling through long station lists. This is consistent with how NAVITIME and Yahoo!乗換案内 present line identity. Not a bug, just a design observation.

**Does a regular user care?** No — this is intentional product design.
