# 4.2 Product Model — Frozen Constitution

## I. 产品定义

Pixel-Tetsudo 是一个**面向日本铁路出行者的路线查询工具**。
核心目的：帮助用户完成交通决策。

> 铁路信息是手段，不是产品目的。

一句话定义：
**帮助用户理解「怎么去、现在能不能坐、这条线是什么、到了之后有什么」。**

---

## II. 页面主心（冻结）

| 页面 | 唯一主心 | 不应该做什么 |
|------|---------|-------------|
| **Home** | 我要去哪里？ | 不抢 Tourism / Realtime 的位置 |
| **Route Search** | 我怎么从 A 到 B？ | 不变成铁路百科、不展示内部字段 |
| **Realtime** | 我现在乘这条线，有没有需要注意的运行状况？ | 不变成线路介绍页面 |
| **Trains** | 这条线是什么、经过哪里？ | 不变成 RailwayDB Viewer |
| **History** | 我刚才查了什么、怎么回来？ | 不变成行为统计面板 |
| **Tourism** | 到了那里以后有什么值得去？ | 不抢交通搜索的主心地位 |

---

## III. Route Search 信息层级（冻结）

| 信息 | 地位 |
|------|------|
| 出发站 / 到达站 | 核心 |
| 路线（使用哪条线） | 核心 |
| 换乘次数 | 核心 |
| 所需时间 | 核心 |
| 站点序列 | 辅助 |
| 运营商名称 | 辅助 |
| OS code | 支持理解 |
| segment 数量 | 不需要 |
| branchOf | 不需要 |
| line_id / station_id | 内部，不出现在 UI |

## IV. 系统规则（4 条宪法）

### 规则 1：能力归属原则
任何系统级能力（线路名解析、站名解析、运营商解析、路线计算、实时状态、景点匹配、语言转换）有且只有一个 Canonical Owner。
页面只能消费，不能私有化复制。

```
RailwayDB.resolveLineName()    ← Owner
RailwayDB.resolveStationName() ← Owner
window.tOp()                   ← Owner
window.DataState.renderList()  ← Owner
```

### 规则 2：数据存在 ≠ 用户需要看到
数据库有字段不代表 UI 必须展示。
每个 UI 元素必须能回答：「普通乘客为什么要看到它？」
答不上来 → REMOVE / HIDE / MOVE to detail。

### 规则 3：反向影响审查
修改任何模块前，必须检查：
- 该模块是否拥有系统级能力？
- 有哪些消费者在使用它？
- 修改后所有消费者是否仍能获得原能力？
- 是否会产生 fallback 或孤儿？
禁止：「为了让 B 跑起来直接改 A，不检查 A 的其他消费者。」

### 规则 4：新增功能不得形成孤岛
新功能必须融入已有的用户任务链。
不允许：「加一个按钮/功能 → 没有对应的用户问题 → 形成孤岛 UI。」

---

## V. 页面关系（冻结）

```
Home
  ↓ 主心：我要去哪里？
  ├── Route Search（主线）
  │     ↓ 完成交通决策
  │     ├── Realtime（查询到达线状态）
  │     ├── Tourism（探索目的地）
  │     └── History（回顾/search）
  └── 次级入口：Trains（网络探索）
```

**关键约束：Tourism 不能出现在 Route Search 卡片内部。**
景点探索是交通任务完成后的独立行为，不是路线结果的附属。

---

## VI. 明确不做的事（冻结）

- 不加时刻表/票价/社交功能
- 不为"数据有字段就显示"增加 UI
- 不以 A 页面为中心改 B 页面
- 不引入新的 displayName 解析路径
- 不做管理员工具
- 不做地图可视化为主界面
