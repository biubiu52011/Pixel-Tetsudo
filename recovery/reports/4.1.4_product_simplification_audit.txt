# 4.1.4 — Product Simplification & Information Hierarchy
# Date: 2026-08-31
# Rule: AUDIT + PROPOSAL ONLY — NO CODE CHANGES YET

---

## Executive Summary

This audit examines every UI element through the lens of "Would a first-time passenger need this?" The result is a prioritized proposal for simplification, not just bug fixes.

**Critical discovery:** The sort mode buttons ( Fewest Transfers / Fastest / Recommended ) are completely non-functional. RouteEvaluator is never defined anywhere in the codebase. BFS finds only ONE route. These 3 buttons are dead UI — they look interactive but do nothing.

---

## Discovery: Dead Code Audit

### Sort Mode Buttons — COMPLETELY DEAD

```javascript
// search-ui.js:13
var currentMode = window.RouteEvaluator ? window.RouteEvaluator.getMode() : 'transfers';
// search-ui.js:96
window.RouteEvaluator.setMode(mode);
self.performSearch();
```

`window.RouteEvaluator` is NEVER defined. No file in js/ defines it. The condition `if (btn && window.RouteEvaluator)` is ALWAYS false. Clicking any sort button does NOTHING.

**User experience:** User sees 3 buttons. Clicks "Fastest." Nothing happens. The route shown is always the BFS-first-found route (unspecified algorithm).

**Verdict:** REMOVE entire sort mode section. It is dead UI.

## Proposed Changes by Category

### BATCH 1: REMOVE (Zero risk, immediate impact)

#### R-01: Sort Mode Buttons
**Location:** search-ui.js lines 10-18, CSS .search-sort-mode/.sort-mode-btn
**Current:** 3 toggle buttons inside every result card
**Proposed:** Remove entirely
**Reason:** Dead code (RouteEvaluator undefined). BFS returns single route. No multi-route comparison possible.
**User impact:** Positive — removes confusion. Users get one result, trust it.
**Migration:** None needed. The buttons do nothing.

#### R-02: Direction Arrows (↑↓)
**Location:** search-ui.js lines 47-50
**Current:** `<span class="line-direction">↑</span>` or `↓` on each ride segment
**Proposed:** Remove
**Reason:** Station order `Tokyo → Takaos` already shows direction. Arrow is zero-information noise.
**User impact:** None — information already present in station sequence.
**Migration:** Delete 4 lines of HTML generation + associated CSS.

#### R-03: Branch Indicator (↳)
**Location:** data-state.js line 43-44
**Current:** `<span class="rs-branch-indicator">↳</span>` shown on Trains cards when `line.branchOf` exists
**Proposed:** Remove
**Reason:** Passengers don't need to know "this line branches from another." They just need to know which line to take.
**User impact:** None — branch relationships are operational details, not passenger information.
**Migration:** Delete 3 lines in data-state.js renderCard().

#### R-04: Train Count Badge (unlabeled number)
**Location:** data-state.js lines 60-64
**Current:** `<span class="rs-status-badge">3</span>` showing count of train positions
**Proposed:** Remove badge entirely
**Reason:** Raw number without label is meaningless. "3" could mean 3 trains, 3 positions, 3 stations with trains. No user can interpret this.
**User impact:** Low — the SVG map already shows train positions visually.
**Migration:** Delete 6 lines in data-state.js renderCard().

### BATCH 2: SIMPLIFY (Reduce complexity, keep function)

#### S-01: Result Header — Remove Segment Count
**Location:** search-ui.js line 6
**Current:** Shows "15 min | 2 segments" in green gradient header
**Proposed:** Show "15 min" only. Remove segment count.
**Reason:** Segment count is redundant with the station timeline below. Users count segments themselves.
**User impact:** Minimal — one less number to process.

#### S-02: Realtime Modal — Collapse Default Sections
**Location:** realtime-view.js openModal()
**Current:** Always shows 4 sections: Status / Interval / Delay Cause / Last Updated
**Proposed:** 
- Normal status: show ONLY status indicator + line name
- Delayed/Suspended: show status + interval + cause
- Last Updated: show only when there IS data
**Reason:** Most users checking realtime just want "is my line on time?" The other fields are noise for normal operations.
**User impact:** Positive — faster scanning, less visual clutter.

#### S-03: Operator Filter — Make Collapsible
**Location:** realtime-view.js renderFilterBar()
**Current:** Always visible horizontal scroll of 21 operator buttons
**Proposed:** 
- Default: show only operators with active data (or "All" + top 3)
- Add "Show all operators" expand button
- On mobile: collapse to single-row scroll
**Reason:** 21 buttons is overwhelming. Most users care about 1-3 operators.
**User impact:** Positive — faster access to relevant filters.

#### S-04: Result Station Timeline — Simplify on Mobile
**Location:** search-ui.js lines 20-30, CSS .station-node/.station-connector
**Current:** Each station is a card with connector lines, [FROM]/[TO] labels
**Proposed:** On mobile (<640px): vertical list without connector lines, without [FROM]/[TO] badges (these are implicit)
**Reason:** Connector lines and badges add visual complexity on small screens where space is precious.
**User impact:** Positive — cleaner mobile experience.

---

### BATCH 3: MOVE (Reposition, don't delete)

#### M-01: Nearby Spots — Move Out of Route Card
**Location:** search-ui.js lines 77-83, renderNearbySpots()
**Current:** Spots injected at bottom of route result card
**Proposed:** After route result card closes, add a standalone "Nearby at [destination]" section with:
- Small header: "Explore [destination]"
- 2-3 top spot cards
- "View all" link to tourism page
**Reason:** Tourism and transit are different intents. Mixing them in one card confuses the information hierarchy.
**User impact:** Positive — clean separation of concerns.

---

### BATCH 4: REDESIGN (Fundamental rethinking)

#### D-01: Home Page — Establish Clear Visual Hierarchy
**Current:** Two equal-weight pixel-cards (search + tourism)
**Proposed structure:**
```
[Header: Pixel Tetsudo]
[Tabs: Search | Status | Trains | History]

─── PRIMARY: Route Search ───
[from] [to] [Search]
(Large, prominent, centered)

─── SECONDARY: Quick Access ───
[Check Realtime Status]  [Browse Lines]

─── TERTIARY: Discover ───
[Sightseeing near a station] (collapsed/less prominent)
```

**Rationale:** 
- Primary task (route search) should dominate the screen
- Realtime and Trains are secondary checks, not co-equal modules
- Tourism is tertiary — only needed when planning activities

**User value:** A first-time user opening the app should immediately know "type stations, hit search." No competing visual elements.

#### D-02: Route Result — Redesign as "Journey Card"
**Current:** duration header + sort buttons + station timeline + segment list + nearby spots
**Proposed structure:**
```
┌─────────────────────────────────┐
│  15 min    東京 → 高尾           │  ← Header: duration + route summary
│  Chuo Rapid Line                 │
│  Tokyo ─────────── Takao         │  ← Visual line diagram
│                                  │
│  ↓ transfer at Tachikawa         │
│                                  │
│  Chuo Rapid Line                 │
│  Tokyo ─────────── Tachikawa     │
│                                  │
│  Sobu Line                       │
│  Tachikawa ─────────── Takao     │
└─────────────────────────────────┘
[Explore Takao]  ← Small action button below card
```

**Key changes:**
1. Remove sort mode buttons (dead code)
2. Remove segment count (redundant)
3. Remove direction arrows (redundant)
4. Replace station timeline with a visual line diagram (like Google Maps Transit)
5. Move nearby spots outside the card as a separate "Explore" action
6. Show transfer stations clearly between segments

**User value:** The user sees their journey at a glance. No cognitive overhead parsing UI chrome.

---

### BATCH 5: HIDE (Until data is ready)

#### H-01: Tourism Grid on Home — Conditional Display
**Current:** Always shows English spot names
**Proposed:** Only show tourism module if:
- At least one spot has a non-English name in the current language, OR
- The user has explicitly enabled tourism
**Reason:** Showing raw English to JA/ZH/KO users breaks trust. Better to hide than show broken content.
**User impact:** Zero for users who never use tourism. Positive for non-EN users who won't see broken names.

## First-Time User Walkthrough (After Changes)

### Scenario: Japanese user searching Tokyo → Takao

1. Opens app → sees large search box (primary)
2. Types "Tokyo" → sees 東京 suggestion
3. Types "Takao" → sees 高尾 suggestion
4. Hits Search
5. Sees ONE result card:
   ```
   15分    東京 → 高尾
   中央線快速
   東京 ─────── 立川
              ↓ 乗換
   -total line diagram -
              ─────── 高尾
   総武線
   ```
6. No buttons to click, no arrows to interpret, no numbers to parse
7. If they want spots near Takao: small "高尾周辺の観光" link below card

### Scenario: English user checking Realtime

1. Opens Realtime tab
2. Sees operator filter: "All | JR East | Tokyo Metro | [+]"
3. Sees line cards grouped by operator
4. Clicks Chuo Rapid Line card
5. Modal opens: "○ Running Normally" — that's it
6. No interval, no cause, no timestamp (those are hidden for normal status)

### Scenario: Chinese user browsing Trains

1. Opens Trains tab
2. Sees 156 lines grouped by operator
3. Each card: OS badge + line name (in Chinese) + interval
4. No branch indicators, no unlabeled numbers
5. Clicks a line → sees SVG map with station names in Chinese
6. Hits back → returns to list
