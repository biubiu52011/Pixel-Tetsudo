## 3. Four Critical Architecture Questions

### Q1: What IS a "Chain"? (Type Definition)

#### 3.1 What a Chain Is NOT

| NOT a Chain | Why | Consequence if confused |
|-------------|-----|------------------------|
| Canonical Line | Defined in railway_data.json, frozen | Would violate Canonical Data Freeze Rule |
| RailwayDB Entity | Queryable via resolveLineName(), persistent | Would create second identity layer |
| LOS Display Group | Defined in line-operation-systems.js, presentation-only | Would conflate display with identity |
| ODPT Operator | API-level aggregation unit | Would collapse line-level granularity |
| Branch Group | Topological relationship, not service continuity | Would incorrectly merge independent status |
| Persistent Database Table | Static data store | Would become second Railway DB |

#### 3.2 What a Chain IS

A **Chain** is a **transient runtime resolution context** - a temporary grouping formed DURING the fusion process that:

1. **Exists only in memory** during a single fuseAll() cycle
2. **Is derived** from Canonical Data + Relation Layer + Topology, never created from scratch
3. **Has no persistent representation** - it is computed, not stored
4. **Can change** between fusion cycles if underlying evidence changes
5. **Is consumed** by the UI layer for display grouping, then discarded

#### 3.3 Type Definition

ResolutionContext (transient, per-line, computed at fusion time):
- canonicalId: string (immutable, from railway_data.json)
- operator: string (immutable, from railway_data.json)
- code: string|null (immutable, from railway_data.json)
- chainGroupId: string|null (computed, e.g., "JR-East_JA")
- chainRole: "primary"|"extension"|"branch"|"standalone" (computed)
- chainConfidence: "CONFIRMED"|"LIKELY"|"POSSIBLE"|"UNKNOWN"|"STANDALONE" (computed)
- chainEvidence: Evidence[] (computed, traceable)
- delayInfo: DelayInfo|null (PER-LINE, NEVER aggregated across chain)
- branchOf: string|null (from canonical data, not computed)
- isAlias: boolean (computed from ALIAS_OF relation)

#### 3.4 Key Boundary: ResolutionContext != ChainDatabase

WRONG (creates second DB):
  window.RunningChainDB = {
    "JR-East_JA": ["Saikyo", "Kawagoe"],
    "JR-East_JK": ["KeihinTohoku", "Negishi"],
    // ... 13 hardcoded chains
  }

RIGHT (runtime computation):
  function resolveChain(lineId, canonicalLines, relations, stationLines) {
    // Compute on-the-fly from evidence
    // Returns ResolutionContext
    // NO persistent storage
  }

### Q2: Evidence Weight Rules - Complete Decision Tree

#### 2.1 Evidence Types and Weights

Each evidence type has a FIXED weight. Weights are ADDED, not multiplied.

| Evidence Type | Weight | Source | Condition |
|--------------|--------|--------|-----------|
| RELATION_THROUGH_SERVICE | +3 | LineServiceRelations | relation == "THROUGH_SERVICE" |
| RELATION_ALIAS_OF | +3 | LineServiceRelations | relation == "ALIAS_OF" |
| RELATION_PHYSICAL_CONNECT | +2 | LineServiceRelations | relation == "PHYSICAL_CONNECT" |
| RELATION_BRANCH_OF | +2 | LineServiceRelations OR canonical branchOf | relation == "BRANCH_OF" |
| TOPOLOGY_SHARED_TERMINAL | +2 | stationLines | Lines share >= 1 station AND at least one is terminal of other |
| TOPOLOGY_SHARED_STATION | +1 | stationLines | Lines share >= 1 station (neither is terminal) |
| CODE_MATCH_SAME_OP | +2 | LINE_TO_OPERATOR + canonical code | Same operator AND same code field |
| CODE_MATCH_DIFF_OP | +0 | LINE_TO_OPERATOR + canonical code | Same code BUT different operators (collision, not match) |
| OPERATOR_MATCH | +0 | LINE_TO_OPERATOR | Same operator alone (necessary but not sufficient) |
| NO_EVIDENCE | 0 | - | No evidence found |

#### 2.2 Negative Evidence (Penalties)

| Negative Evidence | Penalty | Condition |
|------------------|---------|-----------|
| CROSS_OPERATOR_NO_RELATION | -5 | Different operators, no declared relation |
| SAME_CODE_DIFF_TOPLOGY | -2 | Same code BUT zero shared stations AND different terminal stations |
| ALIAS_CONFLICT | -3 | Same name BUT different operator OR different station sets |

#### 2.3 Decision Tree

For each pair of lines (A, B):

Step 1: Check Relations Layer
  IF relation(A,B) == "ALIAS_OF": Resolution = ALIAS, Confidence = HIGH, Action = Deduplicate
  IF relation(A,B) == "THROUGH_SERVICE": Resolution = THROUGH_CHAIN, Confidence = CONFIRMED, Action = Same chain, AGGREGATE delay
  IF relation(A,B) == "PHYSICAL_CONNECT": Resolution = CONNECTED_CHAIN, Confidence = CONFIRMED, Action = Same chain, INDEPENDENT delay
  IF relation(A,B) == "BRANCH_OF": Resolution = BRANCH_CHAIN, Confidence = based on evidence, Action = Same chain, INDEPENDENT delay
  IF relation(A,B) == "UNKNOWN": Resolution = UNPROVEN, Confidence = UNKNOWN, Action = Keep separate
  IF no relation: Continue to Step 2

Step 2: Compute Evidence Score
  score = 0
  IF same_operator(A, B): score += 0 (necessary condition)
  IF same_code(A, B) AND same_operator(A, B): score += 2
  IF shared_station(A, B) AND terminal_shared(A, B): score += 2
  IF shared_station(A, B): score += 1
  IF cross_operator AND no_relation: score -= 5
  IF same_code AND no_shared_station: score -= 2

Step 3: Apply Threshold
  IF score >= 3: Resolution = CONFIRMED_CHAIN, Delay = AGGREGATE (only if THROUGH_SERVICE)
  IF score == 2: Resolution = LIKELY_CHAIN, Delay = INDEPENDENT, UI = warning indicator
  IF score == 1: Resolution = POSSIBLE_CHAIN, Flag for review
  IF score <= 0: Resolution = STANDALONE, Delay = INDEPENDENT

Step 4: Special Override Rules
  IF alias detected (same name + same operator + identical stations): Force ALIAS
  IF cross-operator with no relation: Force STANDALONE
  IF branchOf field exists in canonical: Force BRANCH_CHAIN

#### 2.4 Critical Rule: Score >= 3 Does NOT Mean "Aggregate Delay"

| Score | Chain Grouping | Delay Aggregation | UI Behavior |
|-------|---------------|-------------------|-------------|
| >= 3 + THROUGH_SERVICE | YES | AGGREGATE | Same badge, same status |
| >= 3 + PHYSICAL_CONNECT | YES | INDEPENDENT | Same badge, independent status |
| >= 3 + BRANCH_OF | YES | INDEPENDENT | Same badge, branch indicator, independent status |
| >= 3 + CODE_MATCH only | YES | INDEPENDENT | Same badge, independent status (code collision) |
| 2 | TENTATIVE | INDEPENDENT | Warning indicator |
| <= 0 | NO | N/A | Standalone card |

**This is the most important boundary rule.** Same chain group != same delay status.

### Q3: Branch vs Through Status Isolation

#### 3.1 Conceptual Difference

| Aspect | Through-Service | Branch | Physical Connect | Alias |
|--------|----------------|--------|-----------------|-------|
| Single train continues | YES | NO | NO (shares stations) | N/A (same train) |
| Same physical track | YES (through handover) | NO (diverges) | YES (shared segment) | YES (identical) |
| Same schedule | YES | NO | MAYBE | YES |
| Same delay causes | YES | NO | MAYBE | YES |
| Same operator | Usually | Always | Always | Always |
| Different destinations | NO | YES | NO | NO |

#### 3.2 Status Aggregation Rules

THROUGH_SERVICE chain:
  -> ALL segments share the SAME delayInfo
  -> If Saikyo is delayed, Kawagoe is ALSO delayed
  -> Rationale: Same physical train, same delay cause

PHYSICAL_CONNECT chain:
  -> Segments may have DIFFERENT delayInfo
  -> If Marunouchi is delayed, MarunouchiBranch may be normal
  -> Rationale: Separate services sharing stations

BRANCH_OF chain:
  -> PRIMARY line and BRANCH lines have INDEPENDENT delayInfo
  -> If ChuoRapid is normal, Ome may be suspended
  -> Rationale: Different trains, different routes after branch point
  -> UI: Show branch indicator on primary, independent status on branch

ALIAS_OF chain:
  -> ONLY ONE canonical identity is displayed
  -> The other is hidden/deduplicated
  -> Rationale: Same physical line, two names

#### 3.3 Runtime Implementation Rule

In fuseLine():
  var resolution = resolveChain(lineId); // Returns ResolutionContext
  var fused = {
    id: lineId,
    // ... canonical fields preserved ...
    delayInfo: computeDelayInfo(lineId),  // PER-LINE, does NOT receive chain context
    chainGroupId: resolution.chainGroupId,
    chainRole: resolution.chainRole,
    chainConfidence: resolution.chainConfidence,
    branchOf: line.branchOf || null,  // FROM CANONICAL, not computed
    isAlias: resolution.isAlias || false,
  };

computeDelayInfo() operates on a SINGLE line. It does NOT look at chain members.
Chain aggregation happens ONLY in the UI layer (if at all).

### Q4: UNKNOWN Persistence Strategy

#### 4.1 What UNKNOWN Means

UNKNOWN is NOT a failure state. It is a LEGITIMATE resolution outcome indicating:
"Insufficient evidence to determine relationship. Default to STANDALONE."

#### 4.2 UNKNOWN Resolution Outcomes

| Scenario | Evidence | Resolution | Persistence |
|----------|----------|------------|-------------|
| Same operator, no shared stations, no relation | 0 points | STANDALONE | Each line independent |
| Cross-operator, no relation | -5 points | STANDALONE | Each line independent |
| Known relation = UNKNOWN confidence | Relation exists but confidence=UNKNOWN | UNKNOWN_CHAIN | Flagged, separate cards |
| Data gap (0 stations) | Cannot verify topology | STANDALONE with gap indicator | Independent, show data gap badge |
| Code collision (same code, different topology) | -2 points | STANDALONE | Each line independent |

#### 4.3 UNKNOWN Should NEVER Be

| NOT an UNKNOWN Outcome | Why |
|------------------------|-----|
| Forced merge into chain | Violates Principle 5 (Unknown > Wrong) |
| Suppressed from display | Hides real data |
| Default to "normal" status | Fabricates data |
| Auto-promoted to CONFIRMED | Violates evidence-based rule |
| Stored as permanent relation | Would pollute Relation Layer |

#### 4.4 UNKNOWN UI Representation

In renderCard():
  if (resolution.chainConfidence === "UNKNOWN") {
    card.dataset.chainConfidence = "unknown";
    card.classList.add("rs-chain-unknown");
    // Show ? indicator or dimmed badge
  }
  if (resolution.chainConfidence === "STANDALONE") {
    card.dataset.chainConfidence = "standalone";
    // Normal display, no chain badge
  }

## 4. Module Boundary Contract

### 4.1 Responsibility Map

| Module | Responsibility | Cannot Do | Depends On |
|--------|---------------|-----------|------------|
| railway_data.json | Canonical line/station identity | Nothing (frozen) | - |
| db-loader.js | RailwayDB (query + display identity) | Create/modify lines | railway_data.json |
| line-service-relations.js | Declared line-to-line relations | Compute relations dynamically | railway_data.json |
| line-operation-systems.js | Display grouping/ordering | Define runtime identity | - |
| odpt-unified.js | ODPT API client + LINE_TO_OPERATOR | Create canonical lines | - |
| data-fusion.js | Fuse canonical + ODPT data | Modify canonical data | All above |
| data-state.js | Render cards/lists | Compute chain identity | DataFusion output |
| line-presentation-service.js | Display order computation | Define runtime chains | LineOperationSystems |
| realtime-view.js | Realtime page rendering | Modify fusion logic | DataFusion + DataState |
| trains-page.js | Trains page rendering | Modify fusion logic | DataFusion + DataState |

### 4.2 New Module: js/running-chain-resolver.js (Proposed)

Responsibility: Compute ResolutionContext for each line at fusion time.

Cannot:
  - Modify railway_data.json
  - Create persistent chain database
  - Aggregate delayInfo across lines
  - Override LineServiceRelations declarations
  - Modify LineOperationSystems

Depends on:
  - RailwayDB (for canonical line data)
  - LineServiceRelations (for declared relations)
  - stationLines (for topology evidence)
  - LINE_TO_OPERATOR (for operator mapping)

Produces:
  - ResolutionContext per line (transient, in-memory)
  - Exposed via window.RunningChainResolver API

Consumed by:
  - data-fusion.js (attaches chain metadata to fused lines)
  - data-state.js (uses chain metadata for rendering)

### 4.3 Data Flow Boundary

CANONICAL LAYER (FROZEN):
  railway_data.json -> db-loader.js -> RailwayDB
  line-service-relations.js -> window.LineServiceRelations
  line-operation-systems.js -> window.LineOperationSystems

RESOLUTION LAYER (NEW - TRANSIENT):
  running-chain-resolver.js
    -> Computes ResolutionContext per line
    -> Uses evidence scoring
    -> Produces: chainGroupId, chainRole, chainConfidence
    -> NEVER stores persistently

FUSION LAYER (MODIFIED):
  data-fusion.js -> fuseLine()
    -> Reads canonical line data
    -> Calls RunningChainResolver.resolve(lineId)
    -> Attaches chain metadata to fused output
    -> Computes PER-LINE delayInfo (unchanged)

STATE/RENDER LAYER (MODIFIED):
  data-state.js -> renderCard() / renderList()
    -> Uses chain metadata for badge/indicator display
    -> Per-line delayInfo remains independent
    -> Branch/alias indicators applied

## 5. Anti-Patterns - What 4.3.36 MUST NOT Do

### 5.1 Forbidden Patterns

| Pattern | Why Forbidden | Alternative |
|---------|--------------|-------------|
| const CHAIN_DB = { ... } | Creates second persistent identity source | Compute ResolutionContext at runtime |
| Pre-generate all 156 chain assignments | Hardcodes results, breaks evidence-based rule | Resolve on-demand per line |
| Store chain data in railway_data.json | Violates Canonical Data Freeze Rule | Store only in Relation Layer (already done) |
| Aggregate delayInfo across chain members in fuseLine() | Breaks branch independence | Keep per-line delayInfo, aggregate only in UI if needed |
| Use LOS codes as chain IDs | Confuses presentation with identity | Generate chain IDs from resolved metadata |
| Modify LineServiceRelations programmatically | Pollutes declarative data layer | Add new relations via data governance process |
| Create window.RunningChainDB | Second Railway DB | Use transient ResolutionContext objects |
| Skip evidence scoring for "obvious" cases | reintroduces assumption-based logic | Always compute score, even if trivial |

### 5.2 Borderline Patterns (Must Justify)

| Pattern | Risk | Mitigation |
|---------|------|------------|
| Cache ResolutionContext between fusion cycles | Could become stale DB | TTL-based invalidation, recompute on data change |
| Store chainGroupId in fused line object | Makes chain semi-persistent | chainGroupId is metadata, not identity |
| Show chain badge even for STANDALONE lines | UI confusion | Only show badge when chainGroupId is non-null |
| Merge alias lines in DOM (one card for two IDs) | Loses individual identity | Keep both IDs, hide alias from default view, show on demand |
