# 4.0.4 — Trains Page: First-Time User IA Audit
# Date: 2026-08-31
# Rule: AUDIT ONLY — NO CODE CHANGES

---

## Executive Summary

The Trains page has a **dual-detail-view architecture problem**: there are two competing implementations — `trains-page.js` (active, simpler) and `trains-detail.js` (unused, richer) — neither of which fully satisfies the user's needs. The active path has a critical language bug in the detail title, while the unused path has orphaned HTML references. Additionally, the region field shows untranslated English strings.

---

## F-T01 🔴 CRITICAL — Detail View Title Hardcodes Japanese Name

**Location:** `js/trains-page.js:215`
```js
if (titleEl) titleEl.textContent = fusedLine.nameJa || fusedLine.nameEn || fusedLine.name;
```

**Problem:** When a user clicks a line card to see details, the detail page title is set to `nameJa` (the raw Japanese field) as the primary value, regardless of the user's selected language. If the user is in EN mode, they see:
```
中央線快速    ← Japanese name, wrong for EN user
```

Instead of:
```
Chuo Rapid Line    ← should be English
```

The fallback chain (`nameJa → nameEn → name`) means Japanese ALWAYS wins as the primary display. This is the same class of bug as F-01 in Route Search and F-R01 in Realtime.

**Correct pattern** (from `trains-detail.js:13-18`):
```js
function getDisplayLineName(line) {
  var _lang = (window.currentLang || 'ja').toLowerCase();
  var _nameKey = 'name' + _lang.charAt(0).toUpperCase() + _lang.slice(1);
  return (line && line[_nameKey]) || (line && line.nameJa) || (line && line.nameEn) || (line && line.name) || (line && line.id);
}
```

**User impact:** High. Non-Japanese users see Japanese text as the primary title. This directly contradicts the i18n work completed in phases 3.73 and 3.87.

**If fixed:** One-line change — replace `fusedLine.nameJa || fusedLine.nameEn || fusedLine.name` with a call to the existing `getDisplayLineName()` function or inline the same logic.

**Category:** TECHNICAL-LEAK / i18n BUG

## F-T03 🟡 QUESTIONABLE — Orphaned trains-detail.js With Broken DOM References

**Observation:** `js/trains-detail.js` exists with a richer detail view implementation including:
- Header with line code badge + status badge
- Info rows (code, operator, region, type, stations, duration)
- SVG station map with loop/branch support

However, this script is **NOT loaded** in `trains.html`. The active detail view comes from `trains-page.js` which has a much simpler implementation.

Furthermore, `trains-detail.js` references DOM IDs that don't exist in `trains.html`:
- `trainsDetailHeader` (not in HTML — HTML has `trainsDetailTitle`)
- `trainsCard` (not in HTML — HTML has `trainsLineListContent`)

If someone were to add `<script src="trains-detail.js">` to trains.html, it would throw JavaScript errors because those elements don't exist.

**User impact:** None currently (script is not loaded). But this is dead code that creates confusion for future maintainers.

**If removed:** No user impact. Code base becomes cleaner.

**Recommendation:** Either integrate the richer detail view from `trains-detail.js` into the HTML, or remove the orphaned script. The current `trains-page.js` detail view is functional but minimal.

**Category:** LEGACY-CODE

## F-T04 🟠 WEAK — Region Field Shows Raw English

**Location:** `js/trains-detail.js:127`
```js
'<div class="info-row"><span class="info-label">' + t("detail.info_region") + '</span><span class="info-value">' + escapeHtml(line.region || "") + '</span></div>'
```

**Problem:** The `region` field in `railway_data.json` contains English strings like `"Tokyo Area"`, `"Saitama Area"`, `"Kanagawa Area"`. There are no translation entries for these values in `translations.js`. Users in JA/ZH/KO see English region names.

**What the user sees (JA mode):**
```
地区: Tokyo Area    ← English in Japanese UI
```

**User impact:** Medium. Region is a secondary piece of information, but seeing English in a Japanese UI breaks the immersion and consistency established by the rest of the i18n system.

**If fixed:** Add region translations to `translations.js` (e.g., `region.tokyo_area`: "東京地区"). Or better: make regions translatable via a lookup table keyed by the raw English value.

**Category:** i18n GAP

## F-T05 🟢 GOOD — SVG Station Map Uses Language-Aware Resolution

**Location:** `js/trains-page.js:136-137`
```js
var _rS = (window.RailwayDB && window.RailwayDB.resolveStationName)
  ? function(id){ return window.RailwayDB.resolveStationName(id, _lang) || id; }
```

**Why it works:** Station names in the SVG map are resolved through `RailwayDB.resolveStationName()` with the current language. A ZH user sees Chinese station names, a KO user sees Korean transliterations, etc.

**Category:** GOOD

## F-T07 🟡 QUESTIONABLE — Detail View Lacks Rich Metadata

**Comparison:** The active detail view (from `trains-page.js`) shows only:
- Title (line name)
- SVG station map

The unused `trains-detail.js` would have shown:
- Line code badge
- Status badge (normal/delayed/suspended)
- Info rows: code, operator, region, type, station count, total duration
- SVG station map

**User impact:** Medium. A user clicking into a line detail wants to know: "What line is this? How many stations? Who operates it? Is it running on time?" The current minimal detail view doesn't answer these questions.

**Industry comparison:** NAVITIME and Yahoo!乗換案内 show line code, operator, station count, and operating status in the detail view.

**Recommendation:** Consider integrating the richer detail view from `trains-detail.js` into the active code path (after fixing its DOM references). Not urgent for RC.

**Category:** INFORMATION_ARCHITECTURE

## F-T11 🔵 INTENTIONAL — No Operator Filter on Trains Page

**Observation:** Unlike Realtime, the Trains page has no operator filter bar. Lines are grouped by operator via `DataState.renderList()` (operator group titles), but there's no interactive filter.

**Analysis:** The Trains page is a reference/browsing tool. Users scan all lines. The Realtime page is a monitoring tool where users filter to their operator. This is a deliberate and reasonable design distinction.

**Category:** INTENTIONAL

---

## F-T12 🟢 GOOD — Cross-Page Consistency via DataState

Both Trains and Realtime use the same `DataState.renderList()` and `DataState.renderCard()`. Card appearance, OS badge, line color, and display name resolution are consistent across pages.

**Category:** GOOD
