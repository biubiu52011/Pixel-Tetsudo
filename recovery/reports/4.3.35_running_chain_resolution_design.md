## 1. Problem Statement

### Current State
The Realtime data pipeline operates at LINE GRANULARITY:
`
ODPT API (operator-level delay) -> LINE_TO_OPERATOR -> fuseLine() -> UI card per line
`
Each of the 156 canonical lines receives its own status badge. There is NO concept of a train continuing across multiple lines.

### The Gap
Real-world train operations frequently cross line boundaries:
- Keihin-Tohoku Line (JK) physically continues as Negishi Line to Ofuna
- Saikyo Line (JA) through-services as Kawagoe Line to Kumagaya
- Seibu Ikebukuro Line (SI) through-services through to Ikebukuro and Seibu-Toshima

The current architecture cannot express:
- "This is one continuous service across two lines"
- "These two line cards should share delay/status information"
- "A train observed on Saikyo at Shibuya is the same train arriving at Kawagoe"

### Why This Matters
Without Running-Chain Resolution:
1. A through-service train shows duplicated/inconsistent status on each line segment
2. Users cannot understand that Saikyo and Kawagoe are one continuous service
3. The LOS (LineOperationSystems) display grouping is a PRESENTATION HACK, not a real identity relationship
4. Route Search already has throughServices field (empty) — this is a reserved schema slot

## 2. Architecture Layers

`
Layer 1: Observation        Raw data from ODPT API (operator-level delay text)
Layer 2: Identity Mapping   LINE_TO_OPERATOR + Line codes + Operator names
Layer 3: Running-Chain Resolution  NEW -- determines which lines form one continuous service
Layer 4: Runtime Train      Aggregated identity for the continuous service
Layer 5: State Aggregation  Combined delay/status across all segments
Layer 6: UI Presentation    Display grouped or separate based on chain membership
`

**Current state:** Layers 1-2 and 4-6 exist. Layer 3 (Running-Chain Resolution) is MISSING.

---

## 3. Core Design Principles

### Principle 1: Canonical Identity Is Immutable
Running-chain resolution NEVER modifies railway_data.json. It works ABOVE the canonical layer, creating derived identities from existing data.

### Principle 2: Evidence-Based, Not Assumption-Based
Every running-chain determination MUST have evidence. No common-sense inference about real-world railway operations unless supported by project data.

### Principle 3: Operator Continuity Is Necessary But Not Sufficient
Same operator across two lines is required for through-service, but NOT sufficient to declare a running chain. Additional evidence is needed.

### Principle 4: Topology Defines Possibility, Relations Define Reality
- stationLines / lineStationOrder define which lines CAN connect (topology)
- LineServiceRelations defines which lines DO connect (semantic relations)
- Running-chain resolution uses BOTH

### Principle 5: Unknown > Wrong
When evidence is insufficient, the system should return UNKNOWN rather than make an incorrect assumption.

## 4. Observation Model

### 4.1 Observation Types

| Type | Source | Granularity | Description |
|------|--------|-------------|-------------|
| OPERATOR_DELAY | ODPT API | Operator-level | Aggregate delay status for entire operator |
| LINE_STATUS | Fuse result | Line-level | Per-line fused status (delayInfo) |
| TOPOLOGY_HINT | stationLines | Station-level | Lines sharing a station |
| RELATION_HINT | LineServiceRelations | Line-pair level | Declared relations (THROUGH_SERVICE, etc.) |
| CODE_MATCH | LINE_TO_OPERATOR | Line-level | Lines sharing the same ODPT line code |
| TIMETABLE_PATTERN | Planned future | Train-level | Train number / vehicle number matching |

### 4.2 Current Data Sources

ODPT API:
  - odpt:TrainTimetable (operator-level)
  - Returns: { odpt:trainInformationText: "..." } per operator
  - NO per-train data (no train number, no vehicle ID, no position)

Project Data:
  - LINE_TO_OPERATOR: lineId -> operator (156 mappings)
  - stationLines: stationName -> [{line_id, station_order}] (1841 entries)
  - lineStationOrder: lineId -> [station_name] (topology)
  - LineServiceRelations: [{lineA, lineB, relation, ...}] (14 relations)
  - LineOperationSystems: operator -> [{code, lineIds, order}] (display grouping)

## 5. Identity Resolution Rules

### 5.1 Identity Candidates

For any given line, the identity resolution considers:
1. Canonical ID (line.id) -- The primary identifier
2. Line Code (line.code) -- ODPT-compatible code (e.g., JK, JA)
3. Operator (line.operator) -- Operating company
4. Name variants (line.name, line.nameEn, line.nameJa) -- Display names
5. Station topology (stationLines[line.id]) -- Physical connections

### 5.2 Chain Formation Rules

#### Rule R1: Same-Operator Topology Continuation

Condition: Two lines share the same operator AND one line terminal station appears in the other line station list (or vice versa).

Evidence sources:
- stationLines: Shared terminal station
- lineStationOrder: One line last station == other line first/last station
- Same operator field
- Same or compatible code field

Confidence: HIGH if both topology and code match; MEDIUM if only operator matches

Example -- Keihin-Tohoku vs Negishi:
  - Same operator: JR-East YES
  - Same code: JK YES (both have code JK)
  - Topology: KeihinTohoku stations include Negishi, Isogo, Shin-Sugita, Yokoami, Konan-dai, Hongo-dai, Ofuna YES
  - NEGISHI canonical entry: 0 stations (DATA GAP)
  - Verdict: THROUGH_SERVICE, confidence MEDIUM-HIGH

Example -- Saikyo vs Kawagoe:
  - Same operator: JR-East YES
  - Topology: Both share Omiya station YES
  - Relation Layer: Saikyo<->Kawagoe THROUGH_SERVICE declared YES
  - Verdict: THROUGH_SERVICE, confidence HIGH

#### Rule R2: Cross-Operator Through-Service

Condition: Two lines of DIFFERENT operators share a handover station and a THROUGH_SERVICE relation is declared.

Evidence sources:
- LineServiceRelations: relation == THROUGH_SERVICE
- stationLines: Shared handover station
- Different operator values (this is what makes it cross-operator)

Confidence: HIGH if both relation and topology match

Example -- Saikyo (JR-East) <-> Sotetsu (Sotetsu) <-> MinatoMirai (MinatoMirai) <-> Rinkai (TWR):
  - Current Relation Layer: NO relations declared for this chain NO
  - Topology: All share Yokohama station YES
  - Verdict: UNKNOWN -- data gap, cannot confirm without declared relations

#### Rule R3: Code Collision Resolution

Condition: Two canonical lines share the same code field AND the same operator.

Implication: These lines are likely the same physical service under different naming conventions.

Confidence: MEDIUM (could be alias, could be legitimate sub-segments)

Example -- KeihinTohoku vs Kanagawa:
  - Both have code JK and operator JR-East
  - But they are DIFFERENT physical lines (different station sets)
  - Verdict: NOT an alias -- same ODPT code mapping, different lines. Code collision is acceptable for ODPT query purposes.

Example -- KeikyuMain vs Sakuragi:
  - Both have name Sakuragi and nameEn Sakuragi Line
  - KeikyuMain has code KM, Sakuragi has no code
  - Relation Layer declares ALIAS_OF YES
  - Verdict: ALIAS -- same physical line, duplicate canonical entry

#### Rule R4: Operator-Level Aggregation (Fallback)

Condition: When no line-level through-service can be determined, ALL lines of the same operator sharing the same ODPT endpoint receive the SAME delay status.

This is the CURRENT behavior.

Confidence: N/A (it is the default, not a resolution)

## 6. Identity Resolution Decision Matrix

| Evidence Available | Resolution | Confidence | Action |
|-------------------|------------|------------|--------|
| SAME operator + shared terminal station + same code | THROUGH_SERVICE | HIGH | Merge into running chain |
| SAME operator + shared terminal station + diff code | SAME_OPERATOR_JOINT | MEDIUM | Group but keep separate cards |
| THROUGH_SERVICE relation + shared station | THROUGH_SERVICE | HIGH | Merge into running chain |
| ALIAS_OF relation | ALIAS | HIGH | Deduplicate identity |
| SAME operator + no topology link | OPERATOR_GROUP | LOW | Same delay info, separate cards |
| Different operators + no relation | SEPARATE | N/A | No chain formation |
| Insufficient evidence | UNKNOWN | NONE | Defer resolution |

### 8.1 Case Study: 京浜東北線 <-> 根岸線 (Keihin-Tohoku <-> Negishi)

Current State:
  - KeihinTohoku: code=JK, operator=JR-East, 47 stations (includes Negishi-area stations)

  - KeihinTohoku already includes Negishi, Isogo, Shin-Sugita, Yokoami, Konan-dai, Hongo-dai, Ofuna in its station list

Resolution:
  1. Same operator (JR-East) YES
  2. KeihinTohoku stations include Negishi-area stations YES
  3. Negishi has 0 stations -- cannot verify topology independently
  4. No explicit Relation Layer entry for this pair
  5. Chain ID suggestion: JR-East_JK (grouped by operator+code)
  6. UI impact: KeihinTohoku and Negishi cards should show identical delay info

## 10. Resolution Algorithm (Design)

### 10.1 Phase 1: Build Chain Graph

Input: All 156 canonical lines + stationLines + LineServiceRelations

Algorithm:
1. For each line, collect: operator, code, station set
2. For each pair of lines with SAME operator:
   a. Check if they share any stations (via stationLines)
   b. Check if one is a terminal continuation of the other
   c. Check if Relation Layer declares THROUGH_SERVICE
   d. Check if they share the same code
3. Build adjacency graph: lineA --[evidence]--> lineB
4. Find connected components = potential running chains
5. Score each chain by evidence strength
6. Filter: only chains with score >= threshold become active

### 10.2 Phase 2: Assign Chain IDs

For each active chain:
  chainId = operator + "_" + sharedCode (if exists)
  or
  chainId = operator + "_" + primaryLineCode
  
  segments = [ {lineId, role, direction} ]
  confidence = weighted score of all evidence

### 10.3 Phase 3: Aggregate State

For each chain:
  delayInfo = union of all segment delayInfos
  (since all segments share the same ODPT operator, they get the same delay)
  realtimePositions = merged from all segments

### 10.4 Phase 4: UI Integration

For each line card:
  if line belongs to a chain:
    show chain badge (e.g., JK) instead of individual code
    link related cards (click one -> highlight all chain members)
    share delay info across chain
  else:
    show individual status (current behavior)

## 11. Confidence Scoring System

| Evidence Type | Weight | Example |
|--------------|--------|---------|
| THROUGH_SERVICE relation (from LineServiceRelations) | +3 | Saikyo<->Kawagoe |
| ALIAS_OF relation | +3 | KeikyuMain<->Sakuragi |
| Same operator + same code | +2 | KeihinTohoku + Negishi (both JK) |
| Same operator + shared terminal station | +2 | Saikyo + Kawagoe (share Omiya) |
| Same operator + no topology link | +0 | Two unrelated JR-East lines |
| Different operators + THROUGH_SERVICE relation | +1 | (future: cross-operator) |
| Insufficient evidence | 0 | Defer to UNKNOWN |

Thresholds:
  Score >= 3: CONFIRMED chain
  Score == 2: LIKELY chain (needs manual review)
  Score == 1: POSSIBLE chain (flag for review)
  Score <= 0: NO chain (separate identities)

## 12. Edge Cases

### 12.1 One-to-Many (Branch Lines)
A primary line branches into multiple successor lines (e.g., ChuoRapid branches to Ome, Itsukaichi, ChuoKonosu).
  - Resolution: Each branch is a SEPARATE chain segment with BRANCH_OF relation
  - UI: Show branch indicator on primary line card
  - Status: Branch lines may have DIFFERENT delay status from main line

### 12.2 Many-to-One (Convergence)
Multiple lines converge at a station but continue as one service (e.g., Saikyo + ShonanShinjuku both pass through Shibuya but diverge afterward).
  - Resolution: NOT a running chain -- different destinations
  - UI: Show as separate cards with shared transfer station indicator

### 12.3 Circle Lines
Yamanote Line forms a loop. Every station is both a start and end point.
  - Resolution: Single-chain self-contained loop
  - UI: Show as single entity, no through-service needed

### 12.4 Cross-Operator Through-Service
Saikyo (JR-East) -> Sotetsu (Sotetsu) -> MinatoMirai (MinatoMirai) -> Rinkai (TWR)
  - Resolution: Currently UNKNOWN -- no relations declared
  - UI: Show as separate cards with transfer indicator
  - Future: When Relation Layer is populated with cross-operator relations, these can be chained

### 12.5 Same Name, Different Lines
Ikebukuro exists as both a Seibu line and a TokyoMetro station. Nikko exists as both a JR line and a Tobu line.
  - Resolution: Disambiguate by operator + station context
  - UI: Show operator prefix in disambiguation

4. Historical data analysis -- No retrospective chain building
5. External data sources -- No GTFS, JORNE, or other API integration
6. Canonical data modification -- railway_data.json remains frozen
7. UI layout changes -- Only status/delay aggregation, no card redesign
