# 4.0 — Product Design Review Framework

**Phase:** Product Design (NOT Engineering)
**Principle:** Every UI element must answer WHY it exists for the user.

---

## Review Philosophy

The engineering phase answered: *Can it work?*
The product design phase answers: *Should it work this way?*

### The Core Question for Every Element
> **"If I'm a first-time user who has never opened this app, why would I understand what this is for?"**

If the answer requires knowing internal concepts like:
- line_id, operator ID, branchOf
- OS codes (JA, JB, JC...)
- RailwayDB, DataState, LineOperationSystems
- CSS class names, JS function names

Then the element has FAILED the test.

---

## 7 Audit Dimensions

### 1. User Habit
- Does this match what users expect from Google Maps Transit, NAVITIME, Yahoo!乗換案内?
- Are there conventions we're violating without reason?
- Would a Japanese commuter feel confused?

### 2. Information Architecture
- Why does THIS information appear HERE?
- Is there duplicate information across elements?
- Is the information hierarchy correct (most important first)?
- Would removing this element lose anything meaningful?

### 3. Industry Convention
- How do major Japanese transit apps present this same information?
- Are our patterns consistent with industry norms?
- When we deviate from convention, is there a clear product reason?

### 4. Visual Hierarchy
- What is the user's FIRST glance target?
- Is it the most important thing?
- Are secondary details visually competing with primary info?
- Does the pixel-art style serve usability or just aesthetics?

### 5. Cross-Page Consistency
- Do Home, Trains, Realtime, Route Search, Tourism share the same visual language?
- Do similar decisions appear the same way across pages?
- Would a user feel like they're in the same product?

### 6. Modern UI Standards
- Are there patterns that feel dated or unnecessarily complex?
- Is information density appropriate for mobile screens?
- Are there "development task" elements that serve no user purpose?

### 7. Product Purpose
- Does every feature exist for the USER or for the DEVELOPER?
- Would deleting this feature harm the user experience?
- Is this feature solving a real user problem or an imagined one?

## Page-by-Page Review Questions

### Home
1. What is the user's PRIMARY task on this page?
2. Do the two modules (Search + Tourism) feel like one product or two?
3. Is the navigation clear for someone who's never been here?
4. Does the language switcher interfere with the primary task?

### Route Search
1. Is the search flow intuitive? (From → To → Results)
2. Are the mode selectors (Fastest/Fewest Transfers/Recommended) clearly explained?
3. Does the result display match what users expect from transit apps?
4. Are transfer instructions clear?

### Realtime
1. What is the user trying to answer? ("Is my line delayed?")
2. Does the filter bar help or hinder?
3. Is the status display immediately understandable?
4. Does the modal add value or just duplicate card info?

### Trains
1. Does the line list help users find what they need?
2. Is the OS ordering intuitive?
3. Does the detail page answer the right questions?
4. Is the SVG map useful or decorative?

### Tourism
1. Is the spot recommendation logic clear?
2. Does the station picker make sense?
3. Are tags (food/shopping/museum) useful?

### History
1. Is the history list actionable?
2. Does "Clear History" feel safe?

### Language / i18n
1. Does switching language feel seamless?
2. Are translations natural, not mechanical?
3. Does the default JA behavior match user expectations in Japan?

### Mobile
1. Is everything tappable on a 390px screen?
2. Does content overflow or get cut off?
3. Are touch targets large enough?
4. Does the pixel-art style scale well on small screens?

---

## Comparison Targets

When auditing, compare against these reference products:
- **NAVITIME**: Best-in-class Japanese transit app
- **Yahoo!乗換案内**: Most widely used in Japan
- **Google Maps Transit**: Global standard
- **Apple Maps**: Clean, minimal approach

For each comparison, ask:
- What do they do better?
- What do we do differently and why?
- Should we adopt their pattern?

---

## Output Format

For each finding, classify as:
`
KEEP      -- current design is correct
IMPROVE   -- works but could be better
REDESIGN  -- fundamental issue needs rethinking
REMOVE    -- no user value, should be deleted
`

And answer:
1. What is the problem?
2. What would the fix look like?
3. What user need does it serve?
4. What industry precedent supports this?
