EXECUTIVE SUMMARY
============================================================

FINDING: The three data access paths serve DISTINCT responsibilities.
They are NOT redundant. A forced merge would break functionality.

Recommended classification:
  UNIFIED_LINES  -> KEEP (raw data source, needed by fusion layer)
  DataLayer      -> KEEP (runtime cache + grouped access, has unique methods)
  RailwayDB      -> KEEP (canonical schema + display identity, has unique queries)

The real issue is NOT three paths but UNCLEAR OWNERSHIP DOCUMENTATION.
New AI developers cannot tell which path to use for which purpose.

============================================================
1. THREE PATHS, DIFFERENT RESPONSIBILITIES
============================================================

## Path 1: UNIFIED_LINES (raw canonical data)
  Owner: db-loader.js (data/core/)
  Type: Raw JavaScript object (line_id -> line_object)
  Content: { KeihinTohoku: {name, nameEn, nameJa, code, color, operator, ...}, ... }
  Methods: NONE (plain object)
  Consumers: 12 direct references across 7 files

  Unique role: CANONICAL DATA SOURCE (read-only, global)
  Used by: DataFusion.fuseAll(), LinePresentationService, fallback chains

## Path 2: DataLayer (runtime cache + grouped access)
  Owner: data-layer.js
  Type: Module with cached state
  Methods: getAllLines(), getLine(), getGroupedLines(), getStationCoords(),
           getCachedPositions(), setCachedPositions(), clearCache()
  Consumers: 10 direct references across 5 files

  Unique capabilities (NOT in RailwayDB):
    - Cached train positions (get/set)
    - Grouped line access by region
    - Station coordinate lookup
    - JSON fetch utility
    - Cache size tracking

  Fallback chain: RailwayDB.getAllLines() -> UNIFIED_LINES
  Role: RUNTIME CACHE LAYER (stateful, position/coords tracking)

## Path 3: RailwayDB (canonical schema + display identity)
  Owner: db-loader.js (data/core/)
  Type: Module with rich query API
  Methods: resolveLineName(), resolveStationName(), getAllLines(), getLine(),
           getLineStations(), getLineStationOrder(), getLineColors(),
           getTransferStations(), getNearbyStations(), getNameMap(),
           getTourism(), getSpot(), getLineDurations(), getSchema(), ...
  Consumers: 28+ references across 10 files

  Unique capabilities (NOT in DataLayer or UNIFIED_LINES):
    - Display name resolution (i18n-aware) <- UNIQUE
    - Station name resolution (i18n-aware) <- UNIQUE
    - Tourism data access <- UNIQUE
    - Station location lookup <- UNIQUE
    - Transfer station queries <- UNIQUE
    - Line duration queries <- UNIQUE

  Role: DISPLAY IDENTITY + CANONICAL QUERY LAYER

============================================================

CURRENT (actual):
  UNIFIED_LINES
       |
       +---> DataLayer (wrapper, adds cache)
       |         |
       |         +---> DataFusion (reads DataLayer, adds ODPT)
       |         |            |
       |         |            +---> DATA_FUSION (runtime object)
       |         |
       |         +---> DataState (renders lines)
       |
       +---> RailwayDB (parallel, adds display identity)
                 |
                 +---> All pages (direct display name calls)

RECOMMENDED (documented intent):
  UNIFIED_LINES (canonical raw data)
       |
       v
  RailwayDB (display identity + relations + tourism)
       |        ^
       v        |
  DataLayer (runtime cache: positions, coords, grouped access)
       |
       v
  DataFusion (realtime merger: ODPT API + local data)
       |
       v
  DataState (rendering engine: delay data, line display)
       |
       v
  Pages (Home/Realtime/Trains/History)

NOTE: RailwayDB and DataLayer are PARALLEL, not sequential.
RailwayDB handles display names. DataLayer handles runtime state.
Both read from UNIFIED_LINES as their data source.

============================================================
4. DUPLICATED RESPONSIBILITY ANALYSIS
============================================================

FINDING: There is NO duplicated responsibility.
The three paths serve DIFFERENT purposes.

What LOOKS like duplication:
  route-search.js uses all three paths

This is NOT duplication. It is a RESILIENCE FALLBACK CHAIN:
  Primary: RailwayDB.getAllLines() (has additional methods)
  Secondary: DataLayer.getAllLines() (has cached state)
  Tertiary: UNIFIED_LINES (raw data, always available)

This pattern is INTENTIONAL and CORRECT for a client-side app
that must work offline or with degraded data.

WHAT IS ACTUALLY DUPLICATED:
  None. The earlier report flagged three paths as a problem,
  but upon deep analysis, each path provides unique value.

8. RECOMMENDED TARGET ARCHITECTURE
============================================================

CANONICAL DATA LAYER:
  railway_data.json -> db-loader.js
    |- window.UNIFIED_LINES (raw data object)
    |- window.RailwayDB (display identity + relations)
    |     Methods: resolveLineName, resolveStationName,
    |            getTourism, getNameMap, getStationLocation, ...

RUNTIME STATE LAYER:
  db-loader.js -> data-layer.js
    |- window.DataLayer (runtime cache)
    |     Methods: getCachedPositions, setCachedPositions,
    |            getGroupedLines, getStationCoords

REALTIME FUSION LAYER:
  data-fusion.js
    |- window.DataFusion (module API)
    |- window.DATA_FUSION (runtime fused data)

RENDERING LAYER:
  data-state.js
    |- window.DataState (rendering engine)

KEY PRINCIPLE:
  RailwayDB = DISPLAY IDENTITY (what the user SEES)
  DataLayer = RUNTIME STATE (what the page NEEDS)
  DataFusion = REALTIME DATA (what the user WANTS to know NOW)

These are THREE SEPARATE CONCERNS. Merging them would violate
separation of concerns.
