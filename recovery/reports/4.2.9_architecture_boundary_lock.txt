## 1. Three-Layer Data Architecture (Confirmed Intentional)

### Layer 1: UNIFIED_LINES — Raw Canonical Source
- Owner: db-loader.js (line 81)
- Type: window global, plain JS object
- Responsibility: Raw canonical line objects from railway_data.json
- Consumers: DataFusion (input), DataLayer init, legacy compat fallback
- Why it exists: DataFusion needs raw line objects as input to fuse with runtime ODPT data. RailwayDB is a query layer, not a data source.
- Rule: Do NOT call resolveLineName on UNIFIED_LINES objects directly. They are raw canonical data without i18n resolution.

### Layer 2: DataLayer — Runtime Cache & Query
- Owner: data-layer.js
- Type: window.DataLayer object
- Responsibility: Cached train positions, grouped line access by region/operator, getAllLines()/getLine(id) as runtime-enriched source
- Unique methods RailwayDB lacks: cached positions, group-by-region, ODPT-fused line objects
- Consumers: data-fusion.js, route-search.js, trains-page.js, realtime-view.js
- Why it exists: Runtime state (positions, delay info fusion) cannot live in RailwayDB which is a static query layer.
- Rule: Use DataLayer for runtime state queries. Use RailwayDB for display identity (names).

### Layer 3: RailwayDB — Canonical Query + Display Identity
- Owner: db-loader.js (lines 128-345)
- Type: window.RailwayDB object
- Responsibility: Station queries, Line queries, Display identity (resolveLineName, resolveStationName, getNameMap), Tourism data, Operator names (via tOp)
- Why it exists: Centralized i18n resolution prevents each page from implementing its own name mapping.
- Rule: All user-visible line/station/operator names MUST go through RailwayDB.resolveLineName() / resolveStationName() / tOp().

### PROHIBITED Patterns (Future AI Trap)
The following patterns MUST NOT appear in new or modified code:
- line.name used for user-visible display (allowed only for internal name-to-ID caching)
- line.nameJa / line.nameEn used directly in UI output
- line.id concatenated into user-visible text without resolution
- Custom getDisplayName() / getDisplayLineName() functions
- Any resolver that does NOT ultimately call RailwayDB.resolveLineName()

### Exceptions (Allowed)
- route-search.js:162 — line.name used for internal _nameToIdCache building (NOT user-visible)
- route-search.js:219 — line.name pushed to internal lines array for adjacency logic (NOT user-visible)

- trains-detail.js:47 — line.id used as SVG filter ID (internal DOM identifier, not user-visible text)

## 6. AI Development Prevention Rules

### Rule 1: No Orphan-Generating Migration
When moving a capability from module A to module B:
1. Identify ALL consumers of A
2. Migrate each consumer to B
3. Verify each consumer works with B
4. Only THEN remove A
5. Run global orphan sweep after removal

### Rule 2: Read-Only First
Every 4.x phase starts with read-only analysis. Code changes only after explicit user approval of the audit report.

### Rule 3: Canonical Data Frozen
railway_data.json (156 lines / 509 stations / 1703 name_map / 93 tourism) MUST NOT be modified. Any missing data is DATA-BLOCKED, not a reason to fabricate content.

### Rule 4: Display Identity Sacred
RailwayDB.resolveLineName() / resolveStationName() / tOp() are the ONLY allowed display name paths. No exceptions for convenience.

### Rule 5: No AB Fusion
Never merge module A and module B into a new module C. Either keep both with clear boundaries, or fully migrate with consumer verification.

### Rule 6: Consumer Preservation Test
For every modification to a shared capability:
- List all consumers before change
- List all consumers after change
- Verify zero consumers degraded or broken
- Verify zero new orphans created

### Rule 7: Future AI Trap Scan
After any change, scan for:
- Old function names still defined but unused
- Old variable names still in scope
- Old CSS classes still defined
- Old HTML IDs still present
- Old comments still describing deprecated patterns
These are not bugs today but will mislead future AI developers.
