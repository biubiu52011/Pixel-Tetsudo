# 4.3.35.2 — Outcome Semantics Amendment

## Purpose
Clarify the semantic boundary between UNKNOWN, STANDALONE, and SEPARATE outcomes.
Resolve the conflict where Score <= 0 was mapped to STANDALONE, making UNKNOWN unreachable.

---

## The Conflict (Before Amendment)

Previous definition:
```
Score >= 3 → CONFIRMED_CHAIN
Score == 2 → LIKELY_CHAIN  
Score <= 0 → STANDALONE
```

Problem: UNKNOWN had no operational path. Any line with insufficient evidence
(score <= 0) would become STANDALONE, making UNKNOWN a theoretical state only.

---

## The Fix: Three-Tier Decision Pipeline

Replace the single Score→Outcome mapping with a three-tier pipeline:

```
Tier 1: Candidate Detection
  ↓ Does any continuity candidate exist for this line?
  ↓
  NO CANDIDATE → STANDALONE (terminal)
  YES CANDIDATE → Continue to Tier 2

Tier 2: Hard Constraint Check
  ↓ Is there conclusive evidence that A and B are DIFFERENT entities?
  ↓
  YES (hard contradiction) → SEPARATE / CONFLICT (terminal)
  NO (no hard contradiction) → Continue to Tier 3

Tier 3: Evidence Scoring
  ↓ Compute confidence score for candidate relationship
  ↓
  Score >= threshold → SAME (with confidence level)
  Score < threshold → UNKNOWN (with flag)
```

---

## Outcome Definitions (Final)

### STANDALONE
**Definition:** No continuity candidate detected. This line has no observed 
relationship to any other line that would suggest shared runtime identity.

**When applied:**
- Line has no declared relation in LineServiceRelations
- Line shares no stations with any other line of same operator
- No topology hint exists

**Properties:**
- Independent delay status
- No chain badge
- No visual grouping

**Example:** Yamanote (no through-service, no branch, standalone circle line)

---

### UNKNOWN
**Definition:** A continuity candidate exists, but evidence is insufficient 
to confirm SAME or determine SEPARATE. The resolver cannot rule out either 
possibility.

**When applied:**
- Candidate detected (e.g., same operator, some topology overlap)
- But evidence score below confirmation threshold
- AND no hard contradiction found

**Properties:**
- Flagged in ResolutionContext as confidence="UNKNOWN"
- Independent delay status (never aggregated)
- Visual ? indicator or dimmed badge
- Never auto-promoted to CONFIRMED

**Example:** TobuNikko ↔ Nikkoku (same operator Tobu, but zero shared stations, 
unknown relation — cannot prove SAME, cannot prove SEPARATE)

---

### SEPARATE / CONFLICT
**Definition:** Conclusive evidence proves these lines are DIFFERENT runtime entities.

**When applied:**
- Hard contradiction detected (e.g., conflicting directions, impossible topology)
- Cross-operator with no relation AND negative evidence
- Alias conflict (same name, different operators)

**Properties:**
- Each line maintains independent identity
- Independent delay status
- May show conflict indicator

**Example:** KeihinTohoku vs Kanagawa (same code JK, same operator, but zero 
shared stations and different topology → SEPARATE despite score >= 0)

---

### SAME (CONFIRMED / LIKELY / POSSIBLE)
**Definition:** Sufficient evidence confirms these lines share runtime identity 
as part of the same continuous service.

**When applied:**
- Hard constraint check passed (no contradiction)
- Evidence score meets threshold
- Relation type determines aggregation behavior

**Properties:**
- Shared chainGroupId
- Delay aggregation determined by relation SEMANTICS, not score
- Visual chain badge

**Aggregation Rule (CRITICAL):**
| Relation Type | Delay Aggregation | Rationale |
|--------------|-------------------|-----------|
| THROUGH_SERVICE | AGGREGATED | Same physical train |
| PHYSICAL_CONNECT | INDEPENDENT | Separate services, shared stations |
| BRANCH_OF | INDEPENDENT | Different trains after branch point |
| ALIAS_OF | DEDUPLICATED | Same physical line, one identity |

**This rule is RELATION-SEMANTIC, not SCORE-BASED.**
A score of 5 with BRANCH_OF relation still produces INDEPENDENT delay.
A score of 2 with THROUGH_SERVICE relation still produces AGGREGATED delay.

---

## Revised Decision Tree

```
For line A, evaluating candidate B:

STEP 1: Candidate Detection
  IF no declared relation AND no shared stations:
    → STANDALONE (for this pair)
  ELSE:
    → Candidate exists, continue

STEP 2: Hard Constraint Check
  IF cross-operator AND no declared relation:
    → SEPARATE (hard contradiction)
  IF same-name AND different operators:
    → CONFLICT (alias conflict)
  IF topology impossible (direction mismatch):
    → SEPARATE
  ELSE:
    → No hard contradiction, continue

STEP 3: Evidence Scoring
  score = computeEvidenceScore(A, B)
  
  IF relation == ALIAS_OF:
    → SAME (ALIAS), confidence HIGH
  IF relation == THROUGH_SERVICE:
    → SAME (THROUGH_CHAIN), confidence based on score
  IF relation == BRANCH_OF:
    → SAME (BRANCH_CHAIN), confidence based on score
  IF relation == PHYSICAL_CONNECT:
    → SAME (CONNECTED_CHAIN), confidence based on score
  
  IF score >= 3 AND no relation declared:
    → SAME (CONFIRMED), confidence HIGH
  IF score == 2 AND no relation declared:
    → UNKNOWN (insufficient evidence)
  IF score <= 0 AND candidate exists:
    → UNKNOWN (weak evidence, but candidate not ruled out)

STEP 4: Set Aggregation Behavior
  IF relation == THROUGH_SERVICE: delayAggregation = AGGREGATED
  IF relation == ALIAS_OF: delayAggregation = DEDUPLICATED
  IF relation == BRANCH_OF: delayAggregation = INDEPENDENT
  IF relation == PHYSICAL_CONNECT: delayAggregation = INDEPENDENT
  IF no relation: delayAggregation = INDEPENDENT (default)
```

---

## Critical Boundary Rules (Unchanged)

1. **Branch ≠ Through** — BRANCH_OF relation never aggregates delay, regardless of score
2. **Physical Connect ≠ Through** — PHYSICAL_CONNECT relation never aggregates delay
3. **Alias = Deduplicate** — ALIAS_OF relation shows one canonical identity
4. **Through = Aggregate** — Only THROUGH_SERVICE aggregates delay across chain
5. **Unknown ≠ Standalone** — UNKNOWN means candidate exists but evidence insufficient; STANDALONE means no candidate detected
6. **Score is confidence, not outcome** — Score determines confidence level, not SAME/UNKNOWN/STANDALONE directly
7. **Relation semantics drive aggregation** — Not score, not chainGroupId, but the declared relation type

## Modified ResolutionContext Type

```typescript
type ResolutionContext = {
  // Identity (immutable, from canonical)
  canonicalId: string;
  operator: string;
  code: string | null;
  
  // Tier 1: Candidate Detection
  hasCandidate: boolean;           // True if any continuity candidate detected
  
  // Tier 2: Hard Constraints
  hasContradiction: boolean;       // True if hard evidence of separation
  contradictionType: string | null; // "cross_operator_no_relation", "alias_conflict", etc.
  
  // Tier 3: Evidence Scoring
  evidenceScore: number;           // Raw score from evidence computation
  confidence: "CONFIRMED" | "LIKELY" | "POSSIBLE" | "UNKNOWN" | "STANDALONE" | "SEPARATE";
  
  // Outcome (computed from all tiers)
  outcome: "SAME" | "UNKNOWN" | "STANDALONE" | "SEPARATE" | "CONFLICT";
  
  // Relation semantics (from LineServiceRelations, immutable)
  relationType: "THROUGH_SERVICE" | "PHYSICAL_CONNECT" | "BRANCH_OF" | "ALIAS_OF" | "UNKNOWN_RELATION" | "NONE";
  
  // Aggregation behavior (derived from relationType, NOT score)
  delayAggregation: "AGGREGATED" | "INDEPENDENT" | "DEDUPLICATED";
  
  // Chain membership (runtime only, transient)
  chainGroupId: string | null;     // Computed from operator + code if same
  chainRole: "primary" | "extension" | "branch" | "standalone";
  
  // UI metadata
  chainBadge: string;              // e.g., "JA" shown on card
  branchIndicator: boolean;        // True if this is a branch line
  aliasIndicator: boolean;         // True if this is an alias
  conflictIndicator: boolean;      // True if hard contradiction detected
  unknownIndicator: boolean;       // True if confidence = UNKNOWN
};
```

## Examples: Revised Classification

| Line Pair | Candidate? | Contradiction? | Score | Relation | Outcome | Delay Aggregation |
|-----------|-----------|----------------|-------|----------|---------|-------------------|
| Saikyo ↔ Kawagoe | YES | NO | 5 | THROUGH_SERVICE | SAME | AGGREGATED |
| KeihinTohoku ↔ Negishi | YES | NO | 4 | NONE (inferred) | SAME | INDEPENDENT* |
| KeihinTohoku ↔ Kanagawa | YES | YES (no shared stations) | 0 | NONE | SEPARATE | INDEPENDENT |
| TobuNikko ↔ Nikkoku | YES | NO | 0 | UNKNOWN | UNKNOWN | INDEPENDENT |
| Yamanote (alone) | NO | N/A | N/A | NONE | STANDALONE | N/A |
| KeikyuMain ↔ Sakuragi | YES | NO | 3 | ALIAS_OF | SAME | DEDUPLICATED |
| Marunouchi ↔ MarunouchiBranch | YES | NO | 4 | PHYSICAL_CONNECT | SAME | INDEPENDENT |

*Note: KeihinTohoku ↔ Negishi is inferred THROUGH continuity (same code JK, same operator, topology support) but since no explicit THROUGH_SERVICE relation is declared, aggregation defaults to INDEPENDENT. To achieve AGGREGATED, an explicit THROUGH_SERVICE relation would need to be added via data governance.
