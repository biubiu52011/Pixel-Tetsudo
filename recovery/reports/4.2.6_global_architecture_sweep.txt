D. DUAL TRUTH ANALYSIS
============================================================

### D1: Line Data Access (3 sources)
  Source A: window.RailwayDB.getAllLines()  -- canonical, preferred
  Source B: window.DataLayer.getAllLines()  -- wrapper around A with fallback
  Source C: window.UNIFIED_LINES            -- raw data, direct access

  Consumers using A directly:  route-search.js, station-resolver.js, search-ui.js
  Consumers using B:          data-fusion.js, data-layer.js callers, realtime-view.js
  Consumers using C directly: data-state.js, trains-page.js, trains-render.js

  VERDICT: Triple access path. RailwayDB is canonical but NOT universally used.
  This creates maintenance risk: if RailwayDB schema changes, only A-path consumers
  break. B and C paths may silently continue with stale assumptions.

### D2: Delay/Status Data (2 sources)
  Source A: DataFusion.computeDelayInfo() -- computes from ODPT API + local status
  Source B: DataState._delayData          -- cached copy, updated via subscription

  Flow: DataFusion.subscribe -> DataState.setDelayData -> DataState.getDelayInfo
  VERDICT: Clean subscription chain. ONE source of truth (DataFusion), one cache
  (DataState). No dual truth here.

### D3: Realtime Positions (2 sources)
  Source A: DataFusion.getRealtimePositions(lineId) -- from ODPT API
  Source B: trains-page.js getRealtimePositions()     -- calls A with fallback to
                                                   DataLayer.getCachedPositions

  VERDICT: Minor dual path. trains-page.js has its own wrapper that adds a cache
  layer on top of DataFusion. Low risk but adds indirection.

### D4: Display Name Resolution (CHECKED CLEAN)
  All 6 consumer sites use RailwayDB.resolveLineName() as primary.
  Fallback chains exist but all degrade to line.id (not raw fields).
  VERDICT: Clean. Single resolver, properly guarded fallbacks.

### D5: Operator Display (CHECKED CLEAN after 4.2.3-FIX)
  All 3 consumer sites use tOp(op) for display.
  84 translation keys added (21 ops x 4 langs).
  VERDICT: Clean.

============================================================
E. TIGHT COUPLING ANALYSIS
============================================================

### E1: history.js <-> SearchUI (TIGHT)
  history.js directly accesses:
    - window.SearchUI.performSearch (overrides it!)
    - window.SearchUI.fromInput (DOM element)
    - window.SearchUI.toInput (DOM element)
    - window.SearchUI.refreshUI()

  This is FUNCTIONAL COUPLING, not just dependency. History injects itself
  into SearchUI by wrapping performSearch. If SearchUI refactors its
  internal structure, history.js breaks.

  RISK: MEDIUM-HIGH. This is an intentional architecture pattern (hook
  injection) but it creates a bidirectional dependency that is fragile.

### E2: trains-page.js <-> DataState (MEDIUM)
  trains-page.js calls window.DataState.renderList() for line list rendering.
  DataState renders using its own card template.
  VERDICT: Acceptable. DataState is the designated renderer.

### E3: All pages <-> RailwayDB (HEALTHY)
  Every page uses RailwayDB.resolveLineName() and resolveStationName().
  VERDICT: Clean single-source pattern.

G. ARCHITECTURE CONFLICT MAP
============================================================

EXPECTED (ideal):
  Canonical Data -> RailwayDB -> All Pages (read-only)
       |
       v
  DataLayer (unified accessor)
       |
       v
  DataFusion (realtime merger) -> DataState (rendering engine)
       |
       +--> TrainsPage (list + detail)
       +--> RealtimeView (filter + list + modal)
       +--> SearchUI (route results)
       +--> History (re-render old searches)

ACTUAL (observed):
  Canonical Data -> db-loader.js -> UNIFIED_LINES (raw global) + RailwayDB
       |
       +--> DataLayer (wrapper with fallback to UNIFIED_LINES)
       |       |
       |       +--> DataFusion (reads DataLayer, ALSO reads UNIFIED_LINES directly)
       |       |       |
       |       |       +--> DATA_FUSION (runtime object, accessed directly)
       |       |
       |       +--> DataState (renders using DataFusion.subscribe)
       |       |       |
       |       |       +--> trains-page.js (calls DataState.renderList)
       |       |       +--> realtime-view.js (reads DataFusion directly)
       |       |
       |       +--> route-search.js (reads RailwayDB directly)
       |       +--> search-ui.js (reads RailwayDB directly)
       |
       +--> StationResolver (reads RailwayDB directly)
       +--> History (reads RailwayDB directly, hooks SearchUI)
       +--> TrainsDetail (reads DataLayer directly)
       +--> trains-render.js (ORPHAN - never loaded)

CONFLICTS:
  1. UNIFIED_LINES exists as BOTH a raw global AND goes through DataLayer
  2. DATA_FUSION (runtime data) and DataFusion (module) are different things
  3. Some consumers read RailwayDB directly, some go through DataLayer
  4. Trains page loads both DataFusion AND DataState; Realtime page loads both too
  5. Security module is completely disconnected

============================================================
L. FINAL PRODUCT JUDGMENT
============================================================

### 1. Does each module have a clear single responsibility?
MOSTLY YES, with these exceptions:
  - DataLayer tries to be both a wrapper AND a fallback provider
  - History module has dual role (history + SearchUI hook)
  - Trains page loads 12 JS files when 6 would suffice

### 2. Is there a clear data flow from canonical data to UI?
NO. Three parallel access paths exist:
  RailwayDB -> some pages
  DataLayer -> some pages
  UNIFIED_LINES -> some pages
  This creates maintenance debt.

### 3. Are there orphan implementations that could trap a new AI?
YES. Two confirmed orphans (trains-render.js, security.js) and one
narrow-scope file (local-railway-data.js) that could be misunderstood.

### 4. Is the product architecturally coherent?
PARTIALLY. The core (RailwayDB -> resolveLineName -> all pages) is clean.
But the periphery (fallback chains, orphan files, tight coupling) creates
risk for future development.

### 5. Recommended immediate actions before 4.2.7
  1. Remove trains-render.js and security.js (orphan cleanup)
  2. Document the three access paths and choose a canonical one
  3. Consider extracting history.js SearchUI hook into a cleaner event system
  4. Decide: keep or remove realtime.css
